# Desktop app full interaction reference

This synthesis is derived from the 50 numbered `reference.json` records in this catalog. It is an index and comparison layer, not a substitute for any per-example motion, state frames, journey, interaction map, accessibility notes, or provenance. Open the numbered record before applying a pattern.

## Evidence method and completion boundary

- The reference floor is one local authentic motion asset, three states extracted from that motion, a six-state first-success path, eight observed interaction roles, a failure/recovery route, accessibility observations and unknowns, and reproducible dimensions, duration/frame count, byte size, and SHA-256.
- Product-owned direct GIF/MP4 assets are retained or clipped without synthesized frames. Other cited recordings are replayed in a Weles Chromium isolation context on the Stado-selected `charless-mac-mini`; the record preserves the recording owner and original URL.
- Scaling, temporal clipping, frame-rate normalization, and direct frame extraction are the only media transformations. No interpolated, generated, or still-image-based animation is used.
- `references.json` is the exact 50-record machine index. Each per-example directory is independently inspectable offline after acquisition.

## Recurring structures, derived across all 50 records

### Runtime and shell distribution

- Electron: 18 examples; Qt: 13; native multi-platform: 11; Flutter: 5; Tauri: 3.
- Thirty-eight references use a sidebar–content–inspector shell, eight use sidebar–content, three use content–inspector, and one is a single-surface layout. The distribution explains why persistent selection plus focal content is the dominant desktop pattern without making it universal.

### Repeated interaction sequence

1. Establish a stable launch context before asking for task input.
2. Select a durable workspace, account, file, server, device, project, collection, or engine.
3. Move focus into the primary composer, editor, canvas, request field, address field, or selection surface.
4. Make task intent inspectable before commitment.
5. Commit explicitly, allow a clearly visible autosave, or begin a continuous transport.
6. Preserve a visible result in the same shell so the user can compare cause with effect.

Across the records, navigation state is usually persistent while content changes. Dense tools retain context through selected rows, tree nodes, tabs, panes, tracks, layers, scenes, packets, or objects. Communication and note tools favor list-detail continuity; creative and engineering tools favor a large canvas with dockable controls; transfer and operational tools prioritize progress and status.

### Feedback and recovery patterns

- Selection feedback precedes destructive or expensive commitment. The highlight, active tab, focused field, canvas target, or selected row is kept visible while the primary action is prepared.
- Immediate actions use local feedback: a message appears, a request status arrives, a document changes, a transport advances, or a resource status updates.
- Longer actions preserve progress in a queue, meter, status bar, timeline, packet list, console, log, or result pane rather than replacing the whole shell.
- Recovery normally backtracks one stable state: return to selection, correct the target or prerequisite, and repeat the same command. This is stronger than a generic retry because the prior input and context remain inspectable.
- Cancellation differs from failure. Cancel or Back closes a transient surface without committing; failure leaves the task incomplete and adds localized status that guides correction.

## Material disagreements between examples

### Explicit confirmation versus direct manipulation

Credential, transfer, connection, import/export, and save flows generally make commitment explicit. Canvas, editor, timeline, mixer, and note flows often apply direct manipulation immediately and rely on undo or autosave. A copied confirmation dialog would slow the latter; silent commitment would make the former unsafe.

### Onboarding versus first meaningful task

Some products expose a true welcome, pairing, connection, vault, engine, or setup wizard. Others launch directly into a reusable workspace. The records therefore normalize on first meaningful success rather than inventing an onboarding carousel where none exists.

### Local-first versus account/service prerequisites

Local editors, file tools, and many Qt/native applications can reach success with a writable file or folder. Messaging, hosted collaboration, remote desktop, synchronized vault, and API/database tools may require an account, peer, server, engine, or endpoint. The prerequisite belongs in the journey and cannot be disguised as a UI-only step.

### Window and pane choreography

Electron communication/workspace products tend to preserve one application shell and swap central detail. Creative and engineering applications add dockable panes, detached windows, modal property surfaces, and mode-specific toolbars. Browser-style tab semantics are applicable only where a document or task can remain independently addressable.

### Continuous motion versus discrete transitions

Media, audio, video, animation, remote desktop, capture, and map/time tools contain continuous motion surfaces. Most productivity tools use discrete state replacement or short direct-manipulation feedback. Continuous playback needs persistent transport and interruption controls; discrete task transitions need stable before/after state and localized completion feedback.

## Motion synthesis

- **Trigger:** confirmation, selection, drag, transport start, request send, connection, or direct edit.
- **Start/end:** every record binds motion to a retained task-ready state and a retained first-success result.
- **Continuity:** authentic source frames are preserved; no synthetic tweening bridges states.
- **Timing classes:** immediate direct feedback; short workspace/pane transition; bounded processing/progress; continuous transport/canvas motion.
- **Interruption/reversal:** Back, Cancel, close, prior selection, stop, pause, or undo is preferred when exposed. Exact mid-transition reversal remains product-specific.
- **Reduced motion:** the retained key frames provide a static study aid, not evidence that a product implements `prefers-reduced-motion`. Product-provided reduced-motion and nonanimated equivalents remain unknown unless explicitly present in a per-example record.

## Accessibility synthesis

The visual evidence supports only limited observations: labels and grouping are visible, selected/result states persist spatially, and the journeys avoid claiming color as the only signal. The captures do not expose programmatic roles, accessible names, live-region announcements, full keyboard order, switch-control behavior, high-contrast behavior, zoom reflow, or screen-reader error recovery. Those are recorded as unknowns rather than inferred from visual polish.

## Applicability boundaries

- Use the dominant three-region shell only when users repeatedly select from a collection and inspect or edit one item. Do not force it onto canvas-first, playback-first, or single-document work.
- Preserve dense information where comparison matters; do not copy density into novice paths without progressive disclosure and focus management.
- Use optimistic or autosaved updates only when undo/reversal is cheap and visible. Security, transfer, connection, publish, and destructive flows need stronger confirmation and durable status.
- Treat platform chrome, menus, keyboard conventions, drag-and-drop, file choosers, notifications, and multiple windows as operating-system adaptations, not decorative variants.
- A short capture proves only the visible path it contains. Authentication, permission prompts, offline behavior, long-running failure, and assistive-technology semantics require separate product evidence.

## How to use this catalog

Choose a product with a matching task shape, then open its numbered README, play the local motion, compare all three states, follow the six-state journey, and inspect the failure/recovery and accessibility unknowns. Only then transfer the pattern. The index below is machine-readable: [`references.json`](references.json).
